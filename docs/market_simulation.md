# On-demand market simulation

The simulator now runs only for a persisted session started from the authenticated trading terminal. Users can request 30, 60, or 120 seconds. The API is `POST /market-simulation/start` with `{"durationSeconds":60}` and `GET /market-simulation/status`; both validate the user's JWT at the gateway and the simulator service.

PostgreSQL stores the session in its own `simulator` schema. A transaction-scoped advisory lock serializes starts, recovery, and cleanup, while a partial unique index prevents two live session rows. The active session has an owner UUID, fencing token, lease deadline, and a fixed server-side expiry. The worker checks the persisted owner/fence before bot submissions and blocks submissions at expiry while retaining cleanup ownership through the 15-second grace period. Before seeding, it reads each instrument's active reference price from the risk service, the source used to enforce price bands. If that endpoint is unavailable, it uses configured starting prices that match the risk service's defaults. Drift is clamped to 8% around the session reference, leaving room for quote spreads inside the 10% risk band. It seeds six maker levels on each side per market (36 total, within the risk service's 50-open-order account limit) and allows up to 15 outstanding taker orders per market. New bot submissions are paced by one shared limiter (8 per second by default, configurable from 1 to 12). Only one worker thread is created for a running session; no simulator polling thread runs while idle.

On completion, the service stops new submissions and queries/cancels active orders using only the maker and taker bot credentials through the existing order API. It waits for cancellation events to settle before those bot accounts are reused, so the order and risk services have released their reservations and open-order counts. Cleanup can take up to 60 seconds; a failure leaves the session in `STOPPING`, blocking a replacement session until a start request retries cleanup after the 15-second grace period. This also recovers abandoned sessions after a service restart without polling while idle. User-owned orders, balances, trades, candles, and market history are not reset or deleted.

## Deployment

The simulator's Flyway migration creates the schema and session table. Kubernetes supplies the existing PostgreSQL credentials and points the service at `currentSchema=simulator`; it also uses the existing `public-key` JWT secret. Deploy the gateway and simulator images with the normal Helm release; no new infrastructure or secret is required. If deploying behind the VPS Nginx configuration generated by `scripts/update_nginx.py`, reload that configuration so `/market-simulation` reaches the gateway. For a local run, set `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, and the existing `SECURITY_JWT_PUBLIC_KEY` as used by the other services. `SIMULATOR_ENABLED=false` disables starts.

Metrics are exported through the existing Actuator/Prometheus endpoint: session starts, start conflicts, failures, recoveries, cleanup failures, and bot submissions/fills tagged by market and bot role. The workload is bounded by the configured 120-second maximum, the three markets, maker depth, taker order cap, and one active worker. Cleanup uses up to 24 short-lived threads with a 60-second settlement bound; a cleanup that cannot be confirmed keeps the session blocked for retry.

The PostgreSQL concurrency test uses Testcontainers and is skipped by Testcontainers when Docker is unavailable. Run it with `gradlew :services:simulator:test` in an environment with Docker to exercise concurrent service instances against PostgreSQL.
